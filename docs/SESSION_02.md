# Session 16: Code Style & Structure Audit — `app/api-gateway/`

## 1️⃣ Executive Summary
The **API Gateway** (`apps/api-gateway/`) is a thin Express‑HTTP‑proxy that forwards requests to downstream services, enforces HTTPS, provides CORS, rate‑limiting, health‑checks, and a WebSocket upgrade proxy. Functionally it works, but the current codebase shows many classic signs of a **single‑file monolith** generated by an LLM rather than a production‑grade SaaS component.  Issues span folder layout, naming consistency, module responsibilities, code style, architecture, logging, type safety, and scalability.  A phased refactor (see Section 15) will bring the gateway in line with clean‑architecture principles and make it maintainable as the number of services grows.

## 2️⃣ Folder Structure Review
| Path | Problem | Severity | Suggested Refactor |
|------|---------|----------|-------------------|
| `apps/api-gateway/src/` (only `main.ts`) | All logic lives in one file → hard to navigate, test, and extend. | **Critical** | Split into logical sub‑folders: `config/`, `middleware/`, `routes/`, `ws/`, `utils/`. |
| `apps/api-gateway/src/assets/.gitkeep` | Empty placeholder, not used. | Low | Delete or repurpose for static assets. |
| `apps/api-gateway/README.md` | Too small, no architectural overview. | Low | Expand to describe purpose, start scripts, and folder layout. |
| `apps/api-gateway/env.example` | Lower‑case file name; env files are conventionally UPPER_SNAKE_CASE. | Medium | Rename to `ENV.EXAMPLE` and document naming rule. |

**Proposed Layout**
```
apps/api-gateway/
├─ src/
│  ├─ config/          # configuration loading/validation
│  ├─ middleware/      # cors, rate‑limiter, https‑enforcer, error‑handler
│  ├─ routes/          # health endpoint, proxy registrations
│  ├─ ws/              # websocket upgrade proxy
│  ├─ utils/           # header serializer, helpers
│  └─ server.ts        # minimal bootstrap (express app, listen)
├─ assets/             # optional static docs / swagger
├─ env.example
├─ package.json
└─ tsconfig.json
```

## 3️⃣ File Naming Audit
| File | Inconsistent Naming | Severity |
|------|--------------------|----------|
| `main.ts` | Generic noun, mixes camel‑case with kebab. | Medium |
| `env.example` | Lower‑case, not clearly an env file. | Medium |
| `assets/.gitkeep` | Not a source file (acceptable). | — |

**Convention:** Use **kebab‑case** for source files (`server.ts`, `config.ts`) and **UPPER_SNAKE_CASE** for environment‑related files.

## 4️⃣ Code Style Audit
### AI‑generated patterns
- Repetitive block comments (`// Fix #20`, `// 1. HTTPS ENFORCEMENT`).
- “Belt‑and‑suspenders” duplicate HSTS header logic.
- Large inline arrow functions (`proxyOptions`, `serializeHeaders`).
- Use of `any` for request/response objects.
- Direct `console.error` / `process.exit` scattered throughout.
- Deeply nested conditional blocks (HTTPS enforcement, CORS handling).
### Recommendations
1. **Separate concerns** – each middleware in its own file with a concise exported function.
2. **Replace `any`** with proper `express.Request`, `express.Response`, and custom types.
3. **Guard clauses** instead of nested `if`s.
4. **Remove duplicated comments**; keep JSDoc on functions.
5. **Use a structured logger** (e.g., `pino`) instead of `console.error`.
6. **Avoid redundant HSTS** – apply once in a security middleware.

## 5️⃣ Readability Audit
| Issue | Location | Why it matters | Suggested fix |
|-------|----------|----------------|--------------|
| Monolithic file (≈282 lines) | `main.ts` | Low discoverability, high cognitive load. | Split into modules ≤ 80 lines each. |
| Mixed responsibilities (config, middleware, routes, WS) | Throughout | Violates Single Responsibility Principle. | Move each concern to its own folder/module. |
| Magic numbers (`15 * 60 * 1000`, `31536000`) | Rate‑limiter, HSTS | Hard to understand. | Define named constants (`FIFTEEN_MINUTES_MS`, `ONE_YEAR_SECONDS`). |
| Repeated `allowedHeaders` array | CORS middleware | Duplicate source of truth. | Extract to `config/headers.ts`. |
| No JSDoc / documentation | Entire file | Future maintainers lack context. | Add brief JSDoc to each exported function. |

## 6️⃣ Architecture Audit
- **Presentation**: Express router is coupled with business‑logic (proxy registration). → Should be thin and delegate to service‑specific proxy modules.
- **Orchestration**: Rate‑limiter, CORS, HTTPS enforcement live alongside routing. → Extract into a middleware pipeline.
- **Infrastructure**: WebSocket upgrade logic is mixed with HTTP server startup. → Move to `ws/` layer.
- **Configuration**: Scattered env reads; no validation. → Central `config` module with schema validation.
- **Error Handling**: Inline error responses; no hierarchy. → Global error‑handling middleware with typed error classes.
- **Logging**: Mixed `morgan` and `console.error`. → Unified structured logger.

## 7️⃣ Dependency Direction Audit
| Dependency | Issue |
|------------|-------|
| `@repo/db-mongo` & `@repo/libs` listed but never used | Unused workspace packages increase bundle size. |
| Direct import of `@repo/env-config` in gateway code | Acceptable, but config should be isolated. |
| No circular imports detected (single file) | — |

**Action:** Remove unused dependencies from `package.json`.

## 8️⃣ Configuration Audit
- Env vars accessed via `ENV.<NAME>` without validation → runtime crashes if missing.
- Hard‑coded fallback URLs (`http://localhost:...`) scattered in code.
- No feature‑flag mechanism.

**Recommendation:** Create `src/config/index.ts` that loads `.env`, validates with `zod`, and exports a typed `GatewayConfig` object. Centralise defaults and feature flags.

## 9️⃣ Error Handling Audit
- Uses `process.on('uncaughtException')` → abrupt exit.
- Proxy errors return 502 with raw message, no error type.
- No retry logic for transient upstream failures.

**Improvements:**
1. Graceful shutdown helper that closes the server before exiting.
2. Define `GatewayError` hierarchy (`UpstreamError`, `ValidationError`).
3. Central error‑handling middleware that formats responses uniformly.
4. Optional retry wrapper for critical upstream calls.

## 🔟 Logging Audit
- `morgan('dev')` is dev‑only and unstructured.
- `console.error` lacks levels, timestamps, request IDs.
- Duplicate HSTS logging.

**Production‑grade approach:**
- Replace `morgan` with `pino-http` (JSON logs) or `morgan('combined')` piped through the structured logger.
- Initialise a singleton logger (`src/utils/logger.ts`) with appropriate level based on `NODE_ENV`.
- Add request‑ID middleware for correlation across HTTP and WebSocket paths.

## 1️⃣1️⃣ Type Safety Audit
- Extensive `any` usage (`req: any`, `proxyOptions: any`).
- Missing interfaces for proxy options and WebSocket helpers.
- No explicit return types for utility functions.

**Steps:**
1. Enable `strict` TypeScript flags.
2. Replace `any` with `express.Request`, `express.Response`, and custom `ProxyOptions`.
3. Add return type annotations for all functions.
4. Introduce enums for fixed sets (e.g., `LogLevel`).

## 1️⃣2️⃣ Dead Code Audit
- Empty `assets/.gitkeep` – not needed.
- Unused workspace packages (`@repo/db-mongo`, `@repo/libs`).
- No other dead functions detected.

**Action:** Delete placeholder assets and prune `package.json`.

## 1️⃣3️⃣ Scalability Audit
- Adding new upstream services currently requires editing the monolithic file → high merge‑conflict risk.
- Rate limiting uses in‑memory store – will not scale horizontally.
- No dynamic service discovery; each service URL is hard‑coded.

**Future‑proofing:**
- Introduce a `services.json` map and loop to register proxies automatically.
- Switch rate limiter store to Redis (or other distributed cache).
- Provide a configuration schema that supports multiple environments and providers.

## 1️⃣4️⃣ Human Code Quality Assessment
The code exhibits several **LLM‑generated hallmarks**:
- Repetitive “Fix #X” comments.
- Over‑defensive checks (double HSTS, explicit exits).
- Large inline arrow functions.
- Generic naming (`proxyOptions`, `writeBadGateway`).
- Lack of modular boundaries.

An experienced engineer would structure the gateway as a set of small, well‑named modules, use strict typing, centralised configuration, and consistent structured logging.  The current style hampers readability, testing, and future growth.

## 1️⃣5️⃣ Prioritised Fix List (Roadmap)
### Phase 1 – Folder & Naming Refactor
- Move `main.ts` → `src/server.ts`.
- Create sub‑folders: `config/`, `middleware/`, `routes/`, `ws/`, `utils/`.
- Rename source files to kebab‑case (e.g., `config.ts`, `cors-middleware.ts`).
- Delete `assets/.gitkeep`.

### Phase 2 – Module Extraction
- Split HTTPS enforcement, CORS, rate‑limiter into separate middleware files.
- Create `routes/health.ts` and `routes/proxy.ts`.
- Move WebSocket upgrade logic to `ws/workerProxy.ts`.
- Add `config/index.ts` with schema validation (zod).

### Phase 3 – Type Safety & Logging
- Replace all `any` with proper types and interfaces.
- Introduce `src/utils/logger.ts` (pino) and replace `console.*`.
- Switch `morgan('dev')` to `pino-http` or `morgan('combined')`.

### Phase 4 – Architecture & Error Handling
- Implement global error‑handling middleware with `GatewayError` hierarchy.
- Add graceful shutdown handling for uncaught exceptions.
- Wire request‑ID middleware for correlation.

### Phase 5 – Scalability Enhancements
- Add `services.json` (or YAML) and auto‑register proxy routes.
- Switch rate‑limiter store to Redis (or compatible distributed cache).
- support feature‑flags via config.

### Phase 6 – Final Polish
- Run dead‑code detection (`ts-prune`) and remove any leftovers.
- Upgrade TypeScript strictness, eliminate remaining `any`.
- Update `README.md` with architecture diagram and contribution guide.
- Add unit tests for middleware and proxy registration.
